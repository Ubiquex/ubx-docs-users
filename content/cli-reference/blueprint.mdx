title: "ubx blueprint"
description: "Build, package, and distribute reusable, parameterized infrastructure patterns."
---

Six real subcommands cover a blueprint's whole lifecycle: authoring it
once, packaging it as a real content-addressed artifact, moving it
between local disk, git, and a real OCI registry, and verifying it
wasn't tampered with along the way.

## Usage

```bash
ubx blueprint describe [dir] [--json]
ubx blueprint build [dir] [--lang go|ts|py|all]
ubx blueprint package <dir> -o <tarball>
ubx blueprint push <tarball> --to oci://<registry>/<repo>:<tag>
ubx blueprint pull <source> <dest>
ubx blueprint verify <dir>
ubx blueprint list [--full-hashes]
```

## Examples

Reading what a blueprint takes and returns, without building, packaging
or running it:

```bash
ubx blueprint describe ci-platform
```

```bash
Blueprint  ci-platform · go · described by schema

▸ entrypoint
    import   github.com/ubx-blueprints/ci-platform
    package  ciplatform
    function CIPlatform(Config) Outputs

▸ params · 2
    queue_name               string         required  [QueueName]
    retention_days           number         optional, default not derivable  [RetentionDays]

▸ outputs · 2
    queue_url                 [QueueURL]
    queue_arn                 [QueueARN]
```

Building a blueprint from its `Ubxfile`:

```bash
ubx blueprint build . --lang all
```

```bash
built 5 resource(s) -> . (go, ts, py: go/bindings.go, go/ciplatform.go, go/go.mod, ts/ciplatform.ts, ts/bindings.ts, py/ciplatform.py, py/bindings.py)
```

Packaging and pushing to a real registry:

```bash
ubx blueprint package . -o ci-platform-v1.tar.gz
ubx blueprint push ci-platform-v1.tar.gz --to oci://ghcr.io/ubiquex/ci-platform:v1
```

```bash
packaged ci-platform -> ci-platform-v1.tar.gz
    content hash sha256:a1b2c3... · 7 file(s)
pushed ci-platform -> oci://ghcr.io/ubiquex/ci-platform:v1
    1.4 MB in 2.2s
    content hash sha256:a1b2c3... · 7 file(s)
```

Pulling elsewhere. A pull from a registry verifies the content hash on
arrival and says so, so `ubx blueprint verify` is not a required second
step for this source:

```bash
ubx blueprint pull oci://ghcr.io/ubiquex/ci-platform:v1 ./ci-platform
```

```bash
pulled oci://ghcr.io/ubiquex/ci-platform:v1 -> ./ci-platform
    1.4 MB in 2.1s
    content hash sha256:a1b2c3... verified · 7 file(s)
```

Re-checking a directory later, which is also the only check available
for a copied directory or a bare tarball:

```bash
ubx blueprint verify ./ci-platform
```

```bash
verified ci-platform
    content hash sha256:a1b2c3... matches · 7 file(s)
```

## Flags

### describe

<ResponseField name="--json" type="boolean">
  Print the derived schema as JSON, exactly as `ubx blueprint package`
  would write it. Only meaningful for a blueprint written as code: an
  Ubxfile blueprint has no derived schema, and `--json` says so rather
  than inventing one.
</ResponseField>

### build

<ResponseField name="--lang" type="string">
  `go`, `ts`, `py`, or `all` (default: all).
</ResponseField>

### package

<ResponseField name="-o / --output" type="string">
  Output tarball path. Required.
</ResponseField>

`package` never includes installed dependencies: `node_modules`,
`vendor`, `venv`, `__pycache__`, and anything dot-prefixed such as
`.git` or `.venv`. It names what it left out:

```bash
packaged ci-platform -> ci-platform-v1.tar.gz
    excluded node_modules (installed dependencies, never blueprint content)
    content hash sha256:a1b2c3... · 3 file(s)
```

They are installed artifacts rather than authored content, and a
blueprint's content hash is its identity. Hashing a dependency tree
would make that identity change every time anyone reinstalled, so
`ubx blueprint verify` would fail on your own working tree after an
ordinary `npm install`.

Nothing reads them at evaluation time either. A blueprint's own npm
dependencies reach evaluation through its `deno.lock` and deno's cache
rather than through a `node_modules` tree, and the Go evaluator ignores
`vendor/` outright.

#### Generating a blueprint's npm lock

For a TypeScript blueprint that declares npm dependencies, `package`
resolves them and writes a `deno.lock` into the directory before hashing
it, so the lock is part of the blueprint's content:

```bash
ubx blueprint package . -o widget-v1.tar.gz
```

```bash
    resolving npm dependencies to generate deno.lock (needs network)
packaged widget -> widget-v1.tar.gz
    generated deno.lock (pins this blueprint's npm dependencies for consumers -- commit it)
    content hash sha256:57df4e... · 4 file(s)
```

<Warning>
**Use `deno install`, not `npm install`, inside a blueprint.**

`npm install` writes a `package-lock.json`. That is an ordinary file, so
it becomes part of the blueprint's content and changes its hash, and
`ubx blueprint verify` will then refuse it. `deno install` writes a
`deno.lock` and a `node_modules`, and `node_modules` is excluded from the
manifest, so the hash is unaffected. `verify` names this cause if you hit
it.
</Warning>

<Warning>
**This step needs network access, and `deno` on your `PATH`.** Packaging
needed neither before. It applies only to a TypeScript blueprint that
declares npm dependencies: every other blueprint, including every one
`ubx blueprint build` generates, still packages entirely offline.
</Warning>

The lock exists so that whoever consumes the blueprint gets the same
bytes you resolved. It travels under the content hash like every other
file, so it cannot be swapped without changing the blueprint's identity.
Commit it.

`package` generates it rather than expecting you to, because `npm
install` does not write one: it writes `package-lock.json`, which deno
does not read. Without this you would have had to run a Deno command
inside a package you think of as an npm package.

### list

<ResponseField name="--full-hashes" type="boolean" default="false">
  Render every hash in full instead of the default 12-character short
  form.
</ResponseField>

`list` reports the local content-addressed cache (`~/.ubx/blueprints`),
one row per source:

```bash
ubx blueprint list
```

```bash
NAME   TAG     HASH           SIZE    USED     SOURCE
ts-bp  v0.1.0  sha256:4260e…  3.3 KB  35m old  oci://ghcr.io/ubx-blueprints/ts-bp
ts-bp  v0.2.0  sha256:7805d…  4.0 KB  12m old  oci://ghcr.io/ubx-blueprints/ts-bp

2 blueprint(s) · 7.2 KB total
```

One row per **source**, not per hash, so a blueprint reached two ways
appears twice. When two tags resolve to the same bytes, the rows differ
only in the `TAG` column and share a hash: one thing, reached two ways.

`SOURCE` omits the tag, since the tag has its own column. On a narrow
terminal a long source is elided from the middle, so the scheme and the
blueprint's own name always survive: `oci://ghcr.i…ci-platform`.

### push

<ResponseField name="--to" type="string">
  OCI destination, e.g. `oci://ghcr.io/ubiquex/ci-platform:v1`. Required.
</ResponseField>

### pull

<ResponseField name="--ref" type="string">
  Git ref (branch/tag/commit), only for a git source.
</ResponseField>

<ResponseField name="--path" type="string" default=".">
  Path within the git repo, only for a git source (default `.`).
</ResponseField>

## Notes

`describe` works on both kinds of blueprint. For one written as code it
DERIVES the schema from the function's own signature, the same
derivation `package` performs, rather than reading back a
`blueprint.schema.json` a previous `package` wrote: the question is what
the blueprint will become, not what it became last time. Deriving parses
declarations only, so it works on a tree whose dependencies were never
fetched. The bracketed name beside each param is the identifier as
written in the source, which a caller constructing a config value needs
and cannot recover from the snake_case name.

`package` is where a code blueprint's schema is derived and written,
before the content hash is computed, so the hash covers it.

`build` parses the pre-resolved `resources:` document exactly once,
regardless of how many languages `--lang` requests, every language
compiles from the same parsed document -- nothing in `build` calls an
LLM. `pull`
resolves four real source forms automatically: a local directory, a bare
tarball file, a git repository, or an `oci://` reference, dest must not
already exist. Authentication for OCI push/pull reuses your existing
`docker login`/`oras login` credentials, this project never asks for a
second login. These subcommands are the whole real surface, there's
none for discovery, no `search`, no `list` against a registry. A
`pull` source is always a ref you already have in hand.

### Sensitive parameters

A parameter can be declared `sensitive`, so its argument is recorded as
given but never recorded as a value. `package` refuses a sensitive
parameter that also has a default, because an `Ubxfile` ships inside the
artifact and the default would be distributed with it. See
[Sensitive Parameters](/concepts/blueprint-sensitive-params).
