Six real subcommands cover a blueprint's whole lifecycle: authoring it
once, packaging it as a real content-addressed artifact, moving it
between local disk, git, and a real OCI registry, and verifying it
wasn't tampered with along the way.

## Usage

```bash
ubx blueprint describe [dir] [--json]
ubx blueprint build [dir] [--lang go|ts|py|all]
ubx blueprint package <dir> -o <tarball>
ubx blueprint push <tarball> --to oci://<registry>/<repo>:<tag>
ubx blueprint pull <source> <dest>
ubx blueprint verify <dir>
```

## Examples

Reading what a blueprint takes and returns, without building, packaging
or running it:

```bash
ubx blueprint describe ci-platform
```

```bash
ci-platform (go, described by schema)

entrypoint
  import   github.com/ubx-blueprints/ci-platform
  package  ciplatform
  function CIPlatform(Config) Outputs

params
  queue_name               string         required  [QueueName]
  retention_days           number         optional, default not derivable  [RetentionDays]

outputs
  queue_url                 [QueueURL]
  queue_arn                 [QueueARN]
```

Building a blueprint from its `Ubxfile`:

```bash
ubx blueprint build . --lang all
```

```bash
built 5 resource(s) -> . (go, ts, py: go/bindings.go, go/ciplatform.go, go/go.mod, ts/ciplatform.ts, ts/bindings.ts, py/ciplatform.py, py/bindings.py)
```

Packaging and pushing to a real registry:

```bash
ubx blueprint package . -o ci-platform-v1.tar.gz
ubx blueprint push ci-platform-v1.tar.gz --to oci://ghcr.io/ubiquex/ci-platform:v1
```

```bash
packaged "ci-platform" -> ci-platform-v1.tar.gz (7 file(s), content hash sha256:a1b2c3...)
pushed "ci-platform" -> oci://ghcr.io/ubiquex/ci-platform:v1 (7 file(s), content hash sha256:a1b2c3...)
```

Pulling and verifying elsewhere:

```bash
ubx blueprint pull oci://ghcr.io/ubiquex/ci-platform:v1 ./ci-platform
ubx blueprint verify ./ci-platform
```

```bash
verified "ci-platform": content hash sha256:a1b2c3... matches (7 file(s))
```

## Flags

### describe

<ResponseField name="--json" type="boolean">
  Print the derived schema as JSON, exactly as `ubx blueprint package`
  would write it. Only meaningful for a blueprint written as code: an
  Ubxfile blueprint has no derived schema, and `--json` says so rather
  than inventing one.
</ResponseField>

### build

<ResponseField name="--lang" type="string">
  `go`, `ts`, `py`, or `all` (default: all).
</ResponseField>

### package

<ResponseField name="-o / --output" type="string">
  Output tarball path. Required.
</ResponseField>

### push

<ResponseField name="--to" type="string">
  OCI destination, e.g. `oci://ghcr.io/ubiquex/ci-platform:v1`. Required.
</ResponseField>

### pull

<ResponseField name="--ref" type="string">
  Git ref (branch/tag/commit), only for a git source.
</ResponseField>

<ResponseField name="--path" type="string" default=".">
  Path within the git repo, only for a git source (default `.`).
</ResponseField>

## Notes

`describe` works on both kinds of blueprint. For one written as code it
DERIVES the schema from the function's own signature, the same
derivation `package` performs, rather than reading back a
`blueprint.schema.json` a previous `package` wrote: the question is what
the blueprint will become, not what it became last time. Deriving parses
declarations only, so it works on a tree whose dependencies were never
fetched. The bracketed name beside each param is the identifier as
written in the source, which a caller constructing a config value needs
and cannot recover from the snake_case name.

`package` is where a code blueprint's schema is derived and written,
before the content hash is computed, so the hash covers it.

`build` parses the pre-resolved `resources:` document exactly once,
regardless of how many languages `--lang` requests, every language
compiles from the same parsed document -- nothing in `build` calls an
LLM. `pull`
resolves four real source forms automatically: a local directory, a bare
tarball file, a git repository, or an `oci://` reference, dest must not
already exist. Authentication for OCI push/pull reuses your existing
`docker login`/`oras login` credentials, this project never asks for a
second login. These subcommands are the whole real surface, there's
none for discovery, no `search`, no `list` against a registry. A
`pull` source is always a ref you already have in hand.
