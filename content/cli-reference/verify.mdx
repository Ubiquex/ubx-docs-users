---
title: "ubx verify"
description: "Independently re-verify the entire ledger's chain integrity, offline."
---

This is the auditor's command, the one that makes "independently
verifiable" a real, checkable claim instead of a slogan. It re-checks
everything without trusting a single already-computed value: every
proposal's own hash against its own ID, every parent link, every sealed
apply record, every redacted marker's real shape. Loopback acceptances
need nothing extra: it re-checks them from the ledger alone.

## Usage

```bash
ubx verify [flags]
```

## Examples

A clean chain:

```bash
ubx verify
```

```bash
verify: 47 proposal(s) checked
chain: intact
acceptance: 3 re-derived, 44 convenience-tier (local), 0 inconclusive
```

A broken link:

```bash
ubx verify
```

```bash
verify: 47 proposal(s) checked
  8224643bbbc5...: hash_mismatch -- recomputed hash does not match parent reference
chain: BROKEN (1 finding(s), see above)
```

A loopback acceptance that checks out:

```bash
ubx verify
```

```bash
verify: 1 proposal(s) checked
chain: intact
acceptance: 1 re-derived, 0 convenience-tier (local), 0 inconclusive
  23f09fe5b62c338e4d309d165b033d8fd70e56499f1091198eb6a7500b04dd0c (loopback): VERIFIED -- the stored render is intact and is exactly what this proposal renders to; it attests presence at the machine, not identity
```

The same ledger after the stored render was deleted:

```bash
ubx verify
```

```bash
verify: 1 proposal(s) checked
chain: intact
acceptance: 1 re-derived, 0 convenience-tier (local), 0 inconclusive
  23f09fe5b62c338e4d309d165b033d8fd70e56499f1091198eb6a7500b04dd0c (loopback): FAILED -- the ledger store holds no render under rendered_hash 2863eceeee2b78f886b0e40b9578aa2361f288f68204b5da2cf3a00fd026ab7d; what the approver saw cannot be shown
verify: 0 chain finding(s), 1 acceptance re-derivation(s) failed -- see above
```

## Flags

<ResponseField name="--ledger-dir" type="string" default=".">
  Root directory containing `ledger/` and `.ubx/` (default `.`).
</ResponseField>

<ResponseField name="--stack" type="string">
  Which stack to verify. Required only for a remote ledger store.
</ResponseField>



<ResponseField name="--json">
  Emit one JSON document instead of human text.
</ResponseField>


## Notes

Local (`yes`-typed) acceptances are honestly reported as
convenience-tier, there's nothing external to independently re-derive
them against. Reporting one as fully "verified" would be exactly the
kind of rounding-up this command exists to refuse. "Couldn't check" and
"checked and found a problem" are always kept distinct, never collapsed
into one result.

## Acceptances from a removed method

Ledgers can hold acceptances made earlier by merging or approving a pull
request (`pr_merge`, `pr_review`). Those methods have been removed, along
with the pull-request workflow that produced them. Their records are
history: they still read, the chain they sit in still verifies, and
`ubx verify` reports them as exactly what they are, never as verified
and never as a failure. They do not change the exit code.

```bash
ubx verify
```

```bash
verify: 2 proposal(s) checked
chain: intact
acceptance: 0 re-derived, 0 convenience-tier (local), 0 inconclusive, 2 from a removed method (not re-verified)
  92875f548398ac39bec2bda8ef74e0930fda2cf8d548eb3ae71d51741b92ee91 (pr_merge): NOT RE-VERIFIED -- pr_merge, approval derived from a merged pull request: a removed acceptance method (UBI-300), recorded as history and no longer re-verifiable
  93b4ca7bd91b1a6f0efd915db98cb3929a399839e9411aa8adf419c5d9f2f9a8 (pr_review): NOT RE-VERIFIED -- pr_review, approval derived from a pull request review: a removed acceptance method (UBI-300), recorded as history and no longer re-verifiable
```

With `--json`, `acceptance.removed_method` counts them and each check
carries `"removed_method": true`.

## Loopback acceptances

A `loopback` acceptance is recorded when someone approves a change on
the approval page the local MCP server serves. Along with the approval,
it records `rendered_hash`: the hash of the exact page the approver was
shown, which the ledger keeps.

`ubx verify` checks three things, offline, from the ledger alone:

1. The stored page exists.
2. It still hashes to `rendered_hash`.
3. Rendering the proposal again produces exactly those bytes.

A pass means the record holds the real page the approval was given on,
and that page is a faithful rendering of the proposal that was accepted,
not a summary someone wrote about it.

It does **not** say who approved. The loopback page proves that someone
at the machine running the server clicked, nothing more, which is why
the approver is recorded as `loopback:presence` rather than a name.
Proving who approved needs a server that holds identity.

Each failure is reported separately, and `--json` names it in `outcome`:

| `outcome` | Result | Meaning |
|---|---|---|
| `verified` | pass | All three checks hold. |
| `rendered_missing` | failed | The ledger no longer holds the page. What the approver saw cannot be shown, so the record is not treated as proven. |
| `rendered_hash_mismatch` | failed | The stored page was altered after it was stored. |
| `rerender_differs` | failed | The page is intact, but the proposal renders to something else with the same renderer. |
| `no_rendered_hash` | failed | The acceptance names no page at all. |
| `renderer_version_changed` | inconclusive | The page is intact, but a different version of the renderer produced it, so this binary cannot reproduce it. Not a failure, and not a pass. |

A failed check exits 1. An inconclusive one does not change the exit code.
