---
title: "ubx revert-plan"
description: "Emit the reconciliation steps for an accepted revert, never applies anything itself."
---

Once a `drift_revert` proposal is accepted, someone still has to
actually make the correction happen in the real cloud. `ubx revert-plan`
never does that itself, it emits exactly what needs to happen: a
human-readable list of every changed attribute, from its current
(drifted) value back to the value the ledger records.

## Usage

```bash
ubx revert-plan <proposal-id> [flags]
```

## Examples

```bash
ubx revert-plan 2ab01fbf11e1
```

```bash
--- plan ---
s.aws_instance.web: ami: "ami-new" -> "ami-old"
s.aws_instance.web: instance_type: "t3.large" -> "t3.medium"

make the correction above in cloud via your own tooling; ubx never makes it for you
```

## Flags

<ResponseField name="--ledger-dir" type="string" default=".">
  Root directory containing `ledger/` and `.ubx/` (default `.`).
</ResponseField>

<ResponseField name="--stack" type="string">
  Which stack's ledger to open. Required only for a remote ledger store.
</ResponseField>

## Notes

This command never writes a file and never touches real infrastructure,
on purpose. Making the actual correction to the live resource is
deliberately left to your own tooling, the executor's trust model
doesn't yet extend to applying a revert automatically.

It exits `0` when the plan is emitted, and `2` on an error. It used to
also offer a corrective `.tf` diff with `--tf-dir`, and exit `1` when
some of it needed manual steps. That went with writeback: there are no
source files for ubx to correct.
