---
title: "ubx plan"
description: "Resolve a hand-written intent file or an SDK program into a reviewable draft, saved for ubx ship."
---

`ubx plan` is the fast, terraform-shaped path through this project's own
four-verb ceremony: it fuses resolving and previewing into one command,
rendering the full receipt right here and saving the result for `ubx
ship` to pick up later by hash. Nothing about it touches the ledger,
it's preview and staging, not a signed decision.

It takes one file and works out what it is from the extension: a
hand-written intent file, or a TypeScript, Go or Python SDK program.
Run it with no argument at all and it finds the program itself,
preferring `stack.ts` (or `stack.go`, `stack.py`) if one is there and
otherwise the only SDK program in the directory. Several programs with
no conventional entry among them are listed, never guessed between.

## Usage

```bash
ubx plan [intent-file] [flags]
ubx plan <entry>.go|.ts|.py
```

## Examples

Planning from a real SDK program:

```bash
ubx plan create_platform.go
```

```bash
Plan  payments · from create_platform.go

  + aws_sqs_queue.pipeline-events create

delta: +1 create(s), ~0 change(s), -0 terminate(s)
blast radius: +1 ~0 -0

ubx-proposal: 45f63ce10849...
next: ubx ship 45f63ce10849...
```

Planning with no arguments, one SDK program found automatically:

```bash
ubx plan
```

```bash
Plan  payments · from create_platform.go
...
```

<ResponseField name="--update-lock" type="boolean" default="false">
  Record whatever each declared blueprint resolves to in
  `.ubx/blueprints.lock`, instead of refusing when it disagrees with
  what is already locked.

  The explicit way past a mismatch, and the only way. `ubx plan` refuses
  a disagreement by default rather than rewriting the lock, because a
  lock that quietly accepts different content records nothing.

  Reach for it when you changed the declaration on purpose. When the
  content moved under a declaration you did not change, find out why
  first: see [Blueprint distribution](/concepts/blueprint-distribution).
</ResponseField>

<ResponseField name="--source / --provider-version / --provider" type="string">
  Same provider selection as `ubx ship`.
</ResponseField>

<ResponseField name="--out" type="string">

</ResponseField>

<ResponseField name="--known-dependent" type="list(string)">

## Notes

The saved plan lives at `.ubx/plans/<hash>.json`, addressed by content
hash, never a name you choose. `ubx ship <hash>` (or any unique prefix
of it) looks there directly. This file is a draft, not a ledger entry,
it carries no weight until something actually accepts or ships it.

### When a plan would change something that was set deliberately

Most of what you declare, `ubx` moves toward. A few things move away from
it on purpose: [`ubx restore`](/cli-reference/restore) puts a resource
back to an earlier head, and accepting a drift revert puts one back to
what the ledger already believed.

Afterwards your declaration and your ledger disagree by design, and the
next plan has no way to know that. It reads your declaration, sees live
state differs, and proposes changing it back. So a restore you shipped on
purpose can be undone by the next routine plan, in a diff that looks
entirely ordinary.

The plan now says so:

```console
  1 resource here was last changed deliberately, away from what your declaration says:
    payments.fake_widget.a  restore to head ce86e3e6cc53… (2026-09-16T14:45:38Z)

  This plan changes it again. If that is what you want, nothing here is wrong.
  If it is not, the declaration it is compared against is what to change.
```

It reports a fact and leaves the decision to you. It does not claim the
plan would undo the restore, because that is not always true: changing one
attribute of a restored resource is not necessarily reversing anything.
Moving forward again after a restore is a normal thing to do.

Nothing appears for an ordinary plan. A resource only counts while the
deliberate change is still what it holds: once an ordinary change lands on
top, the note stops, and an accepted-but-unshipped restore never triggers
it because it has not set anything yet.
