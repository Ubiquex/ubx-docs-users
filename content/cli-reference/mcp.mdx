title: "ubx mcp"
description: "Serve ubx over MCP: read your ledger, author blueprints, and propose changes a human approves."
---

`ubx mcp` runs the same binary in server mode, serving the Model Context
Protocol over stdio so an AI assistant can ask real questions about your
infrastructure, and help author a blueprint, directly in conversation,
without you first translating "who changed this bucket" into the right
CLI flags yourself.

Fourteen tools are exposed, in three groups. Four are read-only against
your ledger and live infrastructure, `why`, `status`, `history`,
`scan`, each producing the exact same JSON shape the equivalent
`--json` CLI flag already does. Five help author a blueprint, `draft_ubxfile`,
`validate_ubxfile`, `build_blueprint`, `list_blueprints`,
`describe_blueprint`, none of which write to a repository or touch live
infrastructure at all.

Five more work on the stacks you start the server to serve with
`--serve`: `stacks`, `state` and `schema` read them, `plan` proposes a
change, and `apply` applies one **a human has already approved**. There
is no tool that approves. Approval happens on a page `ubx mcp` serves on
your own machine, which no tool can reach.

## Usage

```bash
ubx mcp [flags]
```

## Examples

Connecting a client (e.g. Claude Code's own MCP config):

```json
{
  "mcpServers": {
    "ubx": { "command": "ubx", "args": ["mcp"] }
  }
}
```

Serving a stack, so an assistant can propose changes to it:

```json
{
  "mcpServers": {
    "ubx": { "command": "ubx", "args": ["mcp", "--serve", "/home/you/stacks/payments"] }
  }
}
```

The server prints where its approval page is to stderr, which most
clients show in their MCP log:

```bash
ubx mcp: approval page at http://127.0.0.1:61540, serving payments
```

Once connected, an assistant can call `ubx_why`, `ubx_status`,
`ubx_history`, or `ubx_scan` directly, the same real ledger data
`ubx why`/`ubx status`/`ubx history`/`ubx scan` would show from your own
terminal, or `draft_ubxfile`/`validate_ubxfile`/`build_blueprint` to
help you author a new blueprint without ever leaving the conversation.

## Now versus what happened

`ubx_status` and `ubx_history` answer two different questions and it is
worth knowing which you are asking for.

`ubx_status` reports what your stack tracks **right now**. A resource
you created and later destroyed is not in it, because it no longer
exists. That is correct, and it means zero resources does not mean an
empty ledger: the proposals that created and destroyed it are still
there permanently.

`ubx_history` reports **what has happened**: every proposal in the
ledger, newest first, including the ones for resources that are now
gone. Each entry carries a proposal ID that `ubx_why` takes directly, so
an assistant can list what happened and then ask for the full detail of
any one decision.

`ubx_status`'s own response includes `proposals_total` for this reason,
so an empty result is never ambiguous: zero resources with a nonzero
`proposals_total` means the stack has history worth reading, not that
nothing was ever here.

`ubx_history` returns 50 proposals by default (500 maximum), newest
first, and always reports `total` and `truncated` so a shortened list is
never mistaken for the whole story.

## Proposing and applying a change

This is the one way an assistant changes infrastructure through ubx, and
it always passes through you.

1. **`stacks`, `state`, `schema`.** The assistant reads what the stack
   holds and what its provider accepts. These see only stacks named with
   `--serve`, by name. A stack the server was not started with does not
   exist as far as they are concerned.
2. **`plan`.** The assistant proposes the change. Nothing is changed. It
   gets back a hash and a link for you:

   ```json
   {
     "format": 1,
     "stack": "payments",
     "proposal_hash": "8eb618522e4e5a635430933cab8427a06b6924555a7ca6f2d7d8189faca2d56d",
     "approval_url": "http://127.0.0.1:61540/approve/payments/8eb618522e4e5a635430933cab8427a06b6924555a7ca6f2d7d8189faca2d56d",
     "blast_radius": { "creates": 1, "modifies": 0, "destroys": 0 },
     "next": "Nothing has been changed. Ask the human to open http://127.0.0.1:61540/approve/payments/8eb618522e4e5a635430933cab8427a06b6924555a7ca6f2d7d8189faca2d56d in a browser on the machine running ubx, read the change, and approve it there if it is right. You cannot approve it yourself. When they say they have, call apply with stack payments and this proposal_hash.",
     "render": "ubx-render proposal/v1\n\nproposal        8eb618522e4e..."
   }
   ```

3. **`apply`, before you approve,** is refused, and changes nothing:

   ```bash
   not applied: nobody has approved this change yet, and nothing was changed. Ask the human to open http://127.0.0.1:61540/approve/payments/8eb618522e4e5a635430933cab8427a06b6924555a7ca6f2d7d8189faca2d56d in a browser on the machine running ubx, read the change, and approve it there if it is right. You cannot approve it yourself. Once they say they have, call apply again with the same proposal_hash
   ```

4. **You open the link and approve.** The page shows the change itself,
   rendered from the proposal, not the assistant's description of it.
   The assistant's own summary is there too, under a heading that says
   it was not checked. A change that destroys anything needs an extra
   confirmation tick.
5. **`apply` again,** and the change ships. The response carries the
   approval:

   ```json
   {
     "format": 1,
     "stack": "payments",
     "proposal_hash": "8eb618522e4e5a635430933cab8427a06b6924555a7ca6f2d7d8189faca2d56d",
     "outcome": "applied",
     "acceptance": {
       "method": "loopback",
       "approvers": ["loopback:presence"],
       "accepted_at": "2026-11-15T19:32:29Z",
       "rendered_hash": "1ac4295779c75c884e05f168ed6dd80c04961d8dcc1a0c35fc0eeca07733e5bc"
     }
   }
   ```

   Calling `apply` again is safe: a change already applied is reported,
   not applied twice.

The approval records `loopback:presence`, meaning someone at this machine
approved, and not who. It also records `rendered_hash`, the hash of the
exact page you were shown, which the ledger keeps.
[`ubx verify`](/cli-reference/verify) checks that page against the
record later.

The page is served only on a loopback address, refuses an approval that
did not come from the page itself in a browser, and cannot be framed by
another site. It does not stop a program with a shell on the same
machine from posting the form, so serve stacks to an assistant in an
environment where that is not a concern.

## Flags

<ResponseField name="--serve" type="string">
  A stack root (a directory holding `.ubx/`, whose `.ubx/config` sets `stack`) that `stacks`, `state`, `schema`, `plan` and `apply` may see. Repeatable. Nothing outside these is visible to them. Without it those five report that nothing is served, and no approval page starts.
</ResponseField>

<ResponseField name="--approval-listen" type="string" default="127.0.0.1:0">
  Where the approval page listens. Must be a loopback IP. Port `0` picks a free port, printed to stderr at startup.
</ResponseField>

The older tools take the stack to run against as a tool input,
`ledger_dir`, not as a server-level setting, see below.

## Which stack a call runs against

`stacks`, `state`, `schema`, `plan` and `apply` run against served
stacks only, named by `stack`. Every other tool that opens a ledger
takes an optional `ledger_dir`. It names
a stack root: the directory holding that stack's `.ubx/` and, once
anything has been accepted, its `ledger/`. That one directory supplies
both the ledger the call reads and the `.ubx/config` it runs under, so
a question about one stack never picks up another stack's provider
settings or ledger store.

Leave `ledger_dir` out and the stack root is the server process's own
working directory, exactly like every other `ubx` command. Point your
MCP client's working directory at a real ledger checkout and an
assistant gets the same defaults a human sitting there would, without
naming a path at all.

Two things an assistant will run into, both deliberate:

- **A path that is not a stack root is refused**, with an error naming
  the path it tried. It is not reported as a stack that happens to
  track nothing. A directory `ubx init` has run in is a stack root even
  before you have shipped anything, and correctly reports zero
  resources.
- **A leading `~/` is expanded** against the home directory of whoever
  the server runs as. An assistant writes `~/stacks/payments` because
  that is how you would write it, and there is no shell in front of an
  MCP call to expand it. `~someone-else/` is refused rather than
  guessed at.

If your MCP client launches the server somewhere unexpected, that
refusal is what you will see, and the error names the directory it
used. That is the fix: set the client's working directory, or have the
assistant pass `ledger_dir` explicitly.

## Notes

`ubx accept`, `ubx ship`, `ubx writeback`, `ubx revert-plan`, `scan
--surface-as`, and `ubx blueprint push` are all deliberately excluded,
and no tool approves a proposal. Accepting a proposal and publishing a
blueprint are both recorded human decisions, never something an
assistant does on your behalf mid-conversation. `apply` ships only what
the ledger already shows you approved. A sensitive attribute is never returned as real
material through any of the three ledger tools, only its salted
fingerprint, the same redaction every other surface in this project
already applies.

`draft_ubxfile`, `validate_ubxfile`, and `build_blueprint` never write
to a repository, no opt-in either, content comes back in the response
itself. See [AI-Assisted Blueprint Authoring](/concepts/mcp-blueprint-tools)
for the full design and why the line sits exactly here.
