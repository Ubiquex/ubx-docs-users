---
title: "ubx mcp"
description: "Serve ubx's ledger and blueprint-authoring tools over MCP, for an AI assistant to call directly."
---

`ubx mcp` runs the same binary in server mode, serving the Model Context
Protocol over stdio so an AI assistant can ask real questions about your
infrastructure, and help author a blueprint, directly in conversation,
without you first translating "who changed this bucket" into the right
CLI flags yourself.

Nine tools are exposed, in two groups. Four are read-only against
your ledger and live infrastructure, `why`, `status`, `history`,
`scan`, each producing the exact same JSON shape the equivalent
`--json` CLI flag already does. Five help author a blueprint, `draft_ubxfile`,
`validate_ubxfile`, `build_blueprint`, `list_blueprints`,
`describe_blueprint`, none of which write to a repository or touch live
infrastructure at all. No tool in either group has execution authority
over a real resource.

## Usage

```bash
ubx mcp
```

## Examples

Connecting a client (e.g. Claude Code's own MCP config):

```json
{
  "mcpServers": {
    "ubx": { "command": "ubx", "args": ["mcp"] }
  }
}
```

Once connected, an assistant can call `ubx_why`, `ubx_status`,
`ubx_history`, or `ubx_scan` directly, the same real ledger data
`ubx why`/`ubx status`/`ubx history`/`ubx scan` would show from your own
terminal, or `draft_ubxfile`/`validate_ubxfile`/`build_blueprint` to
help you author a new blueprint without ever leaving the conversation.

## Now versus what happened

`ubx_status` and `ubx_history` answer two different questions and it is
worth knowing which you are asking for.

`ubx_status` reports what your stack tracks **right now**. A resource
you created and later destroyed is not in it, because it no longer
exists. That is correct, and it means zero resources does not mean an
empty ledger: the proposals that created and destroyed it are still
there permanently.

`ubx_history` reports **what has happened**: every proposal in the
ledger, newest first, including the ones for resources that are now
gone. Each entry carries a proposal ID that `ubx_why` takes directly, so
an assistant can list what happened and then ask for the full detail of
any one decision.

`ubx_status`'s own response includes `proposals_total` for this reason,
so an empty result is never ambiguous: zero resources with a nonzero
`proposals_total` means the stack has history worth reading, not that
nothing was ever here.

`ubx_history` returns 50 proposals by default (500 maximum), newest
first, and always reports `total` and `truncated` so a shortened list is
never mistaken for the whole story.

## Flags

This command takes no flags. Which stack a call runs against is a tool
input, `ledger_dir`, not a server-level setting, see below.

## Which stack a call runs against

Every tool that opens a ledger takes an optional `ledger_dir`. It names
a stack root: the directory holding that stack's `.ubx/` and, once
anything has been accepted, its `ledger/`. That one directory supplies
both the ledger the call reads and the `.ubx/config` it runs under, so
a question about one stack never picks up another stack's provider
settings or ledger store.

Leave `ledger_dir` out and the stack root is the server process's own
working directory, exactly like every other `ubx` command. Point your
MCP client's working directory at a real ledger checkout and an
assistant gets the same defaults a human sitting there would, without
naming a path at all.

Two things an assistant will run into, both deliberate:

- **A path that is not a stack root is refused**, with an error naming
  the path it tried. It is not reported as a stack that happens to
  track nothing. A directory `ubx init` has run in is a stack root even
  before you have shipped anything, and correctly reports zero
  resources.
- **A leading `~/` is expanded** against the home directory of whoever
  the server runs as. An assistant writes `~/stacks/payments` because
  that is how you would write it, and there is no shell in front of an
  MCP call to expand it. `~someone-else/` is refused rather than
  guessed at.

If your MCP client launches the server somewhere unexpected, that
refusal is what you will see, and the error names the directory it
used. That is the fix: set the client's working directory, or have the
assistant pass `ledger_dir` explicitly.

## Notes

`ubx accept`, `ubx ship`, `ubx writeback`, `ubx revert-plan`, `scan
--surface-as`, and `ubx blueprint push` are all deliberately excluded.
Accepting a proposal and publishing a blueprint are both recorded human
decisions, never something an assistant does on your behalf
mid-conversation. A sensitive attribute is never returned as real
material through any of the three ledger tools, only its salted
fingerprint, the same redaction every other surface in this project
already applies.

`draft_ubxfile`, `validate_ubxfile`, and `build_blueprint` never write
to a repository, no opt-in either, content comes back in the response
itself. See [AI-Assisted Blueprint Authoring](/concepts/mcp-blueprint-tools)
for the full design and why the line sits exactly here.
