---
title: "Cross-Stack Orphan Protection"
description: "A destroy can be refused because of a reference in a stack you never touched."
---

Imagine destroying a VPC that a completely different team's stack still
references, their own subnet, their own security group rule, pointing
at a resource that's about to disappear. Nothing in *your* stack would
ever show that danger. The reference lives entirely in theirs.

## How it works

Before a destroy resolves, ubx checks whether any *other* stack you name
still holds a pinned reference to the address being destroyed. Name a
neighbor stack's own ledger directory, and the resolver walks that
neighbor's real, current references, refusing the destroy outright if
one still points at your target.

Name them once, in `.ubx/config`, next to everything else that is true
of your stack rather than of one command:

```hcl
known_dependents = ["../payments", "../security"]
```

Every command that resolves a destroy reads it: `terminate`, `plan`,
`resolve`, `promote`, `restore`. `promote` reads the *target's* config,
since a destroy resolved there orphans whoever depends on the target.

`--known-dependent` still works and **adds to** that list rather than
replacing it, for a neighbor that matters to one destroy only:

```bash
ubx terminate network.aws_vpc.main --known-dependent ../scratch-stack
```

```bash
terminate: network.aws_vpc.main is still referenced by
payments.aws_subnet.public-a (@network.aws_vpc.main.id) -- resolve or
remove that reference first
```

## Why checking only your own stack doesn't work

A destroy that only ever validates against its own stack's own history
has no way to know a neighbor depends on it at all, cross-stack
references are precisely the kind of connection that crosses outside
what any one ledger can see on its own. Refusing to even try checking
would leave exactly the failure mode this exists to prevent: a resource
destroyed out from under a reference nobody thought to look for.

## What this actually looks like

This is best-effort and explicit, not automatic. Naming no neighbors
doesn't mean "no dependents exist," it means none were checked, and ubx
tells you so at both moments you're deciding, in the plan receipt and
again at the ship confirmation just above the prompt:

```
blast radius: +0 ~0 -1
warning: no dependent stacks were checked, so another stack may still
reference network.aws_vpc.main -- set known_dependents in .ubx/config,
or pass --known-dependent <ledger_dir>, to check before destroying
```

When the check does run, it says what it walked:

```
cross-stack check: no stack in ../payments, ../security references
network.aws_vpc.main
```

Both are recorded in the resolved proposal too, as
`status: "not_performed"` or `status: "checked_clear"` with the
directories listed, so a reviewer reading the proposal months later sees
exactly how much protection that destroy actually had.

The positive line matters as much as the warning. Without it, a clean
check and a version of ubx that performs no check at all would look
identical from the output.

## Why it matters

A destroy that only ever looks at its own history could quietly break
something real in another team's stack. Naming this check explicitly,
and recording honestly whether it ran, means a reviewer always knows
exactly how much protection a given destroy actually had, never an
assumed guarantee that wasn't really checked.
