---
title: "Provider Acquisition"
description: "Fetching and verifying real provider binaries before they're ever trusted."
---

Before ubx can talk to a real cloud, it needs the real provider binary
that speaks that cloud's own protocol. Downloading and running an
executable from the internet, without checking it, is exactly the kind
of thing worth being careful about.

## How it works

A provider binary is downloaded from its real registry and its
signature verified before it's ever launched. An unverified or tampered
binary is refused outright, never silently trusted:

```
# .ubx/config.hcl
thirdparty_providers = {
  "hashicorp/aws" = "6.54.0"
}
```

Once acquired, that specific version is cached locally and reused across
every stack on the same machine. A version pinned in your own config
always resolves to the exact binary that version implies, never a
substitute.

## The two things a provider pin controls

For providers ubx ships its own schemas for, there are two versions, and
only one of them is yours to pin.

**The schema snapshot version is yours**, and it behaves exactly as above.
`version = "4.0.0"` resolves to 4.0.0, always. It is part of what gets
reviewed and recorded when you accept a proposal, so it never moves under
you.

**The binary that reads that snapshot is not.** Every snapshot records
which build of ubx's provider server produced it, and ubx runs the newest
release compatible with that record rather than that exact build. It never
crosses a major version.

This matters when a bug is found in the server itself rather than in a
schema. Without it, a fix cannot reach you until every published snapshot
is regenerated and re-released, which is a version bump on work that
changed no schema. Real example: a serialization bug that made a resource
get created in the cloud and then fail on the way back was fixed and
released within the hour, and could not have reached a single stack,
because every published snapshot named an older build.

If you need a byte-identical rebuild of an earlier run, set
`UBX_PROVIDER_DYNAMIC_EXACT=1` and ubx runs precisely the build each
snapshot records. Either way the exact binary that ran is recorded in the
proposal, so `ubx why` can always tell you what produced a reading rather
than leaving you to infer it.

## Why skipping verification would be a real risk

A provider binary is a real, running executable with real access to
your credentials and your infrastructure. Trusting a download without
checking its signature means trusting that nothing between the registry
and your machine ever tampered with it, a real, avoidable risk for
something with that much reach.

## What this actually looks like

The verified binary's own checksum is recorded alongside the
observations it produces:

```bash
ubx why payments.aws_sqs_queue.pipeline-events
```

```bash
source: document create_platform.go, content_hash=sha256:9f2a...
```

`ubx why` can eventually show not just who signed a change, but which
exact, verified tool actually read the state behind it, the checksum is
already recorded in the ledger's own resolution data, whether or not
every view of it renders that detail today.

## Why it matters

Every real cloud call ubx makes goes through a binary that was
downloaded once, verified once, and never silently substituted, giving
the whole chain of trust a real, checkable foundation underneath it.
