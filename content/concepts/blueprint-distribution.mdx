---
title: "Distributing a Blueprint"
description: "Package, push, and pull a blueprint through a real OCI registry, no new server required."
---

A blueprint that only exists on its author's own laptop isn't
reusable, it's just a file. The moment someone else needs to call it,
from a different machine, a different repo, a different team, there
has to be a real, verifiable way to hand it to them that survives the
trip intact.

## How it works

`ubx blueprint package` turns a built blueprint directory into a
content-addressed tarball. `ubx blueprint push` uploads that tarball,
unmodified, to any real OCI registry, GHCR, Docker Hub, Artifactory,
Harbor, whichever one your team already uses:

```bash
ubx blueprint package . -o ci-platform-v1.tar.gz
ubx blueprint push ci-platform-v1.tar.gz \
  --to oci://ghcr.io/acme/ci-platform:v1
```

```bash
packaged ci-platform -> ci-platform-v1.tar.gz
    content hash sha256:a1b2c3... · 7 file(s)
pushed ci-platform -> oci://ghcr.io/acme/ci-platform:v1
    1.4 MB in 2.2s
    content hash sha256:a1b2c3... · 7 file(s)
```

Anyone with registry access pulls it back down the same way, on any
machine. A pull from a registry checks the content hash on arrival, so
confirming nothing changed in transit is not a second step:

```bash
ubx blueprint pull oci://ghcr.io/acme/ci-platform:v1 \
  ./ci-platform
```

```bash
pulled oci://ghcr.io/acme/ci-platform:v1 -> ./ci-platform
    1.4 MB in 2.1s
    content hash sha256:a1b2c3... verified · 7 file(s)
```

That check is not the same as the one the registry already did. A
registry verifies the blob's own digest, which proves the bytes arrived
as it stored them. The content hash is the blueprint's own, computed
from its files when it was packaged, and it is what says these are the
bytes the author shipped.

`ubx blueprint verify` remains the way to re-check a directory at any
later time, and the only check available for the two delivery paths
that have no registry behind them: a copied directory and a bare
tarball.

```bash
ubx blueprint verify ./ci-platform
```

```bash
verified ci-platform
    content hash sha256:a1b2c3... matches · 7 file(s)
```

## Declaring a blueprint, and pinning what it resolved to

Pulling by hand works, and for a stack you keep coming back to there is
a better path. Declare the blueprint in `.ubx/config` and ubx pulls it
for you, at plan time, before anything evaluates:

```hcl
blueprints = {
  ci-platform = "oci://ghcr.io/acme/ci-platform:v1"
}
```

The same four source forms `ubx blueprint pull` accepts all work here:
an `oci://` reference, a `git+https://` URL with an optional `@ref` and
`#subdirectory=`, a `file://` path, or a bare local path.

Your stack then imports it by name, in whichever language it is written
in:

```typescript
import { ciPlatform } from "ci-platform";
```

```go
import bp "github.com/acme/ci-platform"
```

```python
from ci_platform import ci_platform
```

No relative path into a directory you pulled by hand, and nothing to
keep in sync. ubx resolves the declaration, verifies it, and makes it
importable before your program runs.

**It does not edit your project's files to do that.** No entry appears
in your `go.mod`, no `node_modules` directory is created, no `deno.json`
is rewritten. Go gets the blueprint through a workspace ubx writes in
its own build directory, TypeScript through an import map ubx generates
and deletes, and Python through the interpreter's path. Those are files
ubx owns, so nothing it does can be undone by an `npm install` or a
`go mod tidy`, and nothing it leaves behind can surprise you later.

`ubx plan` then records what that declaration actually resolved to, in
`.ubx/blueprints.lock`:

```json
{
  "schema_version": 1,
  "stacks": {
    "platform": {
      "ci-platform": {
        "source": "oci://ghcr.io/acme/ci-platform:v1",
        "content_hash": "sha256:a1b2c3..."
      }
    }
  }
}
```

**Commit that file.** It is the only thing that lets a colleague, or CI,
or you on a different machine, get the same blueprint you did. The
declaration says where to look; the lock says what was found there.

From then on `ubx plan` and `ubx resolve` check the blueprint against
the lock and refuse if it disagrees, rather than quietly using something
else. A tag like `:v1` can be repointed at any time, and that is the
whole reason this exists.

Two disagreements read differently, because they mean different things:

```
blueprint "ci-platform" in stack "platform" is locked to
oci://ghcr.io/acme/ci-platform:v1 but is now declared as
oci://ghcr.io/acme/ci-platform:v2 -- the declaration changed and
blueprints.lock is behind; re-run with --update-lock to record the new source
```

That one is ordinary. You changed the declaration, and `ubx plan
--update-lock` records the new one.

The other is not:

```
blueprint "ci-platform" in stack "platform" resolved to sha256:9f8e7d...,
but blueprints.lock locks it to sha256:a1b2c3..., from the same source
oci://ghcr.io/acme/ci-platform:v1.
The declaration did not change, so the content behind it did.
```

Nobody edited anything and the content moved anyway. Either the tag was
repointed, or the registry is serving different bytes than it served
before. Find out which before you accept it. `--update-lock` is there,
and it is deliberately the last thing that message mentions.

A stack with no lock file yet is not affected by any of this. The first
`ubx plan` writes one, and enforcement starts once it exists.

### What the lock buys, beyond a record

Blueprints are cached locally by content hash, one directory per hash,
never per name or tag. A tag is a pointer that can be repointed at any
time, so it names storage for nobody. Your lock file is what resolves a
tag to a content hash.

That has a consequence worth knowing. A **locked** blueprint resolves
from the cache without asking the registry anything, because "do I
already have exactly this content" is a question your machine can answer
by itself. An **unlocked** one cannot: nothing local can know what a tag
points to now, so it is fetched every time.

The cache used to be keyed on the declaration instead, and the way that
failed is not the way anyone would guess. It did not overwrite one
version with another. A cache hit checked the stored copy against its
own manifest, which always succeeds, so the registry was never asked
again: whichever version you pulled first stayed on your machine
indefinitely, while a colleague pulling for the first time got the
current one. Both machines verified successfully. Neither had any way to
notice they disagreed.

A wrong file you can find. A machine quietly a version behind, forever,
diverging from everyone else's according to who pulled when, you cannot.

`ubx blueprint list` shows what is cached, one row per source, with the
hash each one resolved to:

```bash
NAME   TAG     HASH           SIZE    USED     SOURCE
ts-bp  v0.1.0  sha256:4260e…  3.3 KB  35m old  oci://ghcr.io/ubx-blueprints/ts-bp
ts-bp  v0.2.0  sha256:7805d…  4.0 KB  12m old  oci://ghcr.io/ubx-blueprints/ts-bp
```

Two tags resolving to the same bytes show as two rows sharing a hash and
a source, differing only in the tag. That is what it is: one thing,
reached two ways.

`requirements.txt` still works for Python stacks and is unchanged. If
the same name appears in both, the `[blueprints]` table wins and says so.

## When a blueprint has dependencies of its own

A blueprint is code, so it can import things. What happens depends on
where those things come from, and the rule is the same whichever file
declared them.

**Something inside the blueprint** always works, with no network and no
ceremony. A relative path in `deno.json`, or a `file:` dependency in
`package.json` pointing at a directory inside the blueprint, is resolved
directly. The target travelled with the blueprint, so it is already
there.

**An npm package** works, on one condition: the blueprint has to pin it.
`ubx blueprint package` writes that pin for you, as a `deno.lock` covered
by the blueprint's content hash, so you get this by packaging normally
rather than by adopting anything.

Before evaluating, ubx fetches those dependencies in a step of their own
and checks them against that lock. Bytes that do not match are refused
before your stack runs:

```bash
blueprint "widget": fetching its npm dependencies failed: exit status 1
    Tarball checksum did not match what was provided by npm registry for left-pad@1.3.0.
```

A blueprint packaged before this existed ships no lock, and is refused
with the command that fixes it:

```bash
blueprint "widget" declares 1 npm dependency(ies) and ships no deno.lock,
so nothing pins what would be fetched:
    left-pad -> npm:left-pad@1.3.0 (in package.json)
  `ubx blueprint package` generates this lock, so re-packaging the
  blueprint is the fix.
```

**A JSR package does not work**, even from a blueprint that pins it.

<Warning>
This is worth knowing before you plan around it, because the published
Ubiquex TypeScript SDK is on JSR.

Evaluation runs deno with `--no-remote`, the flag that stops an evaluated
program loading code from a URL at runtime. It does not block npm, but
resolving a JSR package fetches `https://jsr.io/<pkg>/meta.json`, which
that flag blocks even when the package is already cached. A lock does not
help, because the problem is not that the graph is unpinned.

Publishing the same code to npm, or vendoring it into the blueprint, are
the two paths that work today.
</Warning>

Direct `https://` and git imports are refused for the same reason.

### What this does and does not pin

The **blueprint's** dependencies become pinned: what it declared, your
machine verified against its lock before anything ran.

Your **stack's own** dependencies are unchanged. They are still resolved
by deno against your own `deno.lock`, exactly as before, and evaluation
still reaches the network for them. The boundary is not that `ubx plan`
stops using the network. It is that a blueprint you did not write cannot
pull in code nobody pinned.

One thing that did change for the better: `ubx plan` no longer rewrites
your `deno.lock`. deno updates a project's lock as a side effect of
running, so evaluating a stack used to leave a diff in a file you own.
ubx now points deno at a copy.

## Why a bespoke registry doesn't need to exist

A tarball pushed to an OCI registry is one manifest wrapping one blob
layer, the exact same shape Helm charts, WASM modules, SBOMs, and
Cosign signatures already use in production. Building a new,
Ubiquex-hosted registry service to store blueprints would mean
standing up and operating real server infrastructure just to
reimplement something every real OCI registry already does correctly.
Reusing that existing infrastructure means any registry your team
already authenticates against, via the same `docker login`/`oras
login` credentials `ubx` reads directly, works as a blueprint backend
with zero new server code.

## What this actually looks like

A push and a pull each carry two separate, non-competing hashes, not
one. OCI's own blob digest, computed and checked natively by the
registry on every round trip, is a transport-level check: did these
exact bytes survive the trip there and back. `blueprint.lock.json`'s
own `content_hash`, the same one `ubx blueprint verify` already
checks, travels inside the tarball itself and stays an
application-level check: is this genuinely the content that was built
and reviewed, unmodified. Recording `content_hash` as an OCI manifest
annotation too means a plain `docker manifest inspect` can cross-check
it without pulling and extracting first, a convenience, never a second
competing verification path.

`ubx blueprint pull` resolves four real source forms the same way,
regardless of which one produced them: a local directory, a bare
tarball file (no network at all, for handing someone a blueprint over
email or a support ticket), a git repository at a given ref, or an
`oci://` reference. Whichever one a teammate used, `ubx blueprint
verify` afterward can't tell the difference.

**Stated plainly:** none of these four is a discovery mechanism. There's
no registry to browse, no `ubx blueprint search`, no way to ask "what
blueprints exist." A caller already has to know the ref, the same way
you already have to know a Docker image tag before you can `docker
pull` it. Distribution here means "get the bytes for a ref you already
have," never "find one."

## Why it matters

Nobody has to trust that a blueprint arrived intact, `ubx blueprint
verify` proves it, the same way `ubx why` proves which blueprint
produced a given resource. And nobody has to stand up or maintain a
new piece of infrastructure to share one: the registry your team
already has is already enough.
